# PC FISH 자동화 모드 0.4.32

0.4.32는 메뉴·목록·교배 성공 화면을 관찰용으로 취급하며, 화면을 닫지 않아도 교배·합성·시즌 제작·레벨업 판단을 계속한다. 실제 통신·확인 대화상자·미확정 요청 보호는 유지한다. 시세와 이력 처리 후 판단 직전에 최신 스냅샷을 다시 읽고 세션·설정 일치를 확인하므로, 부가 처리 시간이 길어졌을 때 오래된 스냅샷으로 반복 대기하지 않는다. 기존 5초 유효성 검사를 완화하지 않는다.

0.4.31의 일반 합성 조건은 **별 등급 동일·희귀도 차이 최대 1·재료 10마리**다. Protected 모드는 같은 희귀도 묶음을 먼저 사용하고, 없을 때만 같은 별 등급의 인접 희귀도 묶음을 찾는다. 클라이언트 예측의 최저 결과 `min(5, floor(희귀도 합계/10)+1)`가 가장 높은 재료보다 낮은 조합은 차단한다. 두 단계 이상 차이 나는 조합은 예측이 좋아도 허용하지 않는다. 경제 모드는 모델에 가장 높은 재료보다 낮은 결과가 하나라도 있으면 추가로 거부한다. 게임도 최신 재료 상태로 재검사한다. 최고 매수 주문 가격·잠금·시즌 예약·교배 부모 선택은 유지한다.

이전 0.4.30의 **희귀도·별 등급 모두 동일한 10마리** 제한은 위 0.4.31 정책으로 대체했다. 어종과 남은 교배 횟수는 달라도 된다. 교배의 부모 선택과 시즌 제작의 레시피 조건은 이번 일반 합성 변경의 영향을 받지 않는다.

0.4.29의 현재 가격 기준은 `market_merge_price_basis=highest_buy_order`다. 같은 어종·별 등급의 **최고 매수 주문 가격에서 수수료를 뺀 수령액**을 사용한다. 교배 횟수가 다른 판매 매물의 최고 호가는 사용하지 않는다. 1,000원 이하이면 교배·합성·시즌 제작 후보로 허용하고, 초과이면 보호한다. 실제 상품별 주문은 `buy_order_proof`의 통화·어종/별 상품명·최고 주문·가격별 주문 수량으로 검증하며, 게임 내부에서도 원자료로 가격을 재계산한다.

원화 금액은 Steam 내부 정수 단위(100단위=1원)를 사용한다. 현재 Steam 공개 클라이언트의 10원 단위 반올림·최소 수수료 규칙을 실제 공개 매물의 Steam/게임 수수료와 대조한 뒤 최고 매수 주문에 맞는 최대 순수령액을 구한다. 수수료 근거가 맞지 않으면 보호한다. 매수 주문이 명시적으로 0건이면 즉시 판매 가치는 0원이고, 누락·조회 오류·잘못된 통화·만료는 0원으로 취급하지 않는다. 이 가격은 조회 시점 주문 기준이며 향후 체결 보장은 아니다.

장터 미등재 신규 일반종의 비교종 정책도 최고 매수 주문 기준으로 바꾼다. 같은 희귀도·별 등급의 기존 일반종 전체를 확인하고, 각 종의 순수령액 중 최댓값을 `estimated_peer_highest_buy_order`로 기록한다. 실측 주문과 추정 가격은 구분하고, 추정 가격으로 영구 잠금을 걸지 않는다. 시즌 완성품·수집 목표·해파리 우선순위·일반 재료 예약과 사용자 잠금은 유지한다.

기존 판매 호가 캐시는 매수 주문 근거가 없으면 재조회한다. 새 조회는 공개 상품 페이지 한 번에서 주문과 수수료 근거를 읽으며 교배 상태별 전체 페이지 수집은 하지 않는다. 상품 간 120초 간격·단일 작업·서버 백오프·24시간 캐시는 유지한다. 갱신 중 아직 매수 가격을 확인하지 못한 상품은 임시 보호한다.

```powershell
& 'C:\Project\PC-fish\scripts\Set-Automation.ps1' -Mode Protected -Protection Market -MergePriceBasis HighestBuyOrder
```

이하 버전별 판매 호가 설명은 기존 정책의 변경 이력이다. 최고 매수 주문 정책에는 위 기준이 우선한다.

0.4.28은 시즌 제작과 재료 예약을 해파리(FS00040) → 프랑켄피시(FS00039) → 아귀(FS00038) 순서로 집중한다. 최우선 미완료 어종의 목표에만 일반 재료를 예약하고, 후순위 일반 재료는 일반 교배·합성에 남긴다. 각 어종의 1~5성 수집 목표와 이미 수집한 모든 시즌 완성품, 사용자 잠금·수동 예약·시세 보호는 유지한다. 우선순위와 현재 집중 어종은 시즌 계획의 `species_priority`·`focus_species`·`focus_name`에 표시한다. [재료 예약과 우선순위](season-crafting.md)를 참고한다.

0.4.27은 성공·무소비 거절·복구가 완료된 요청의 전체 재고 스냅샷과 강한 네이티브 콜백 참조를 해제한다. 미확정 요청은 필요한 근거를 유지한다. 완료된 콜백은 요청 ID와 IL2CPP 약한 생존 핸들만 보관해 중복·지연 응답을 차단하며, 객체가 수거되면 해당 핸들도 정리한다. 네이티브 주소가 다른 콜백 객체에 재사용된 경우에는 이전 요청으로 오인하지 않는다. 상태 파일의 `response_bindings_active`와 `response_bindings_settled`로 활성·완료 추적 수를 확인할 수 있다.

0.4.26은 Steam의 교배 상태별 검색으로 현재 판매 중인 최고 상태를 확인하고, 그 상태의 매물을 다음 페이지까지 모두 읽어 최고 판매자 호가를 계산한다. 먼저 상품 전체 판매 수량을 읽고, 잔여 0회·1회·2회 순서로 각 상태의 판매 수량을 확인한다. 상태별 수량의 합이 상품 전체 수량과 일치하고 마지막 전체 수량 재조회도 같을 때만 전체 상태를 확인했다고 인정한다. 실제 판매 상태에서 멈추므로 이론상 최대 횟수가 있는 매물을 요구하지 않는다. 가격 내림차순을 요청해도 환산 가격에 작은 순서 역전이 있을 수 있으므로 이를 오류로 취급하지 않고, 최고 상태 전체의 고유 매물 ID와 가격을 모아 최댓값을 직접 구한다.

`coverage_version=3`과 `best_state_proof`에 전체 수량 전후 값, 상태별 판매 수량, 정확한 검색문, 정렬 방향, 조회한 가격·교배 상태·매물 ID를 남긴다. 네이티브 실행 측도 수량의 합, 연속 상태 범위, 최고 상태의 전체 고유 매물 수를 대조하고 직접 최고 상태·가격을 계산한다. 최고 상태의 첫 20건만 있는 이전 근거는 다시 수집한다. 첫 저가 페이지와 신규종의 부분 비교 시세는 이 근거를 대체하지 않는다. 초기 상품 페이지는 기존 개체 시세·최근 거래 정보용으로만 유지하며 조회용 Chrome은 매번 종료한다. 최고 상태의 추가 조회는 로그인 없이 공개 읽기 요청으로 진행한다.

상품 간 2분 간격·단일 조회 작업·내부 조회 간 5초 간격·서버 백오프와 24시간 시세 캐시는 유지한다. 상태 검색의 부분 진행은 `market-book-progress/states-*.json`에 남긴다. 기존 전체 페이지 수집 근거(`coverage_version=2`)도 계속 검증하며 원본은 보존한다.

0.4.24는 첫 페이지의 소진된 저가 매물을 최고 교배 상태의 시세로 잘못 사용하던 문제를 수정한다. Steam 공개 프런트엔드의 읽기 전용 `QueryListingsForItem` 조회를 이용해 다음 커서를 끝까지 이어 읽고, 현재 상품의 전체 판매 매물에서 가장 큰 잔여 교배 횟수를 찾는다. 그 상태인 매물들의 최고 판매자 호가를 합성 보호와 신규종 예상 가치의 근거로 사용한다. 이론상 만교배 매물이 실제로 판매 중일 것을 요구하지 않으며, 모든 매물이 소진됐다면 전체 조회 후에만 0회 상태를 최고 상태로 인정한다.

상품 간 기존 2분 간격은 유지하고, 한 상품의 페이지는 5초 간격으로 순차 조회한다. Chrome과 로그인 정보는 사용하지 않는다. 중간 수집 위치와 이미 본 매물 ID는 `market-book-progress`에 보존해 재시작 후 이어 읽는다. 같은 가격의 매물 순서 변화와 일반 판매로 생기는 페이지 중복은 ID로 정리하고, 빠진 범위를 다시 읽어 관측한 판매 수량에 필요한 고유 매물을 확보한다. 조회 시작·완료 시각과 수집 중 최소·최대 판매 수량을 함께 남긴다. 아직 범위가 부족하거나 교배 상태·통화가 잘못된 경우에는 조회 완료로 인정하지 않는다. 서버 제한 응답은 기존 백오프를 따른다. 첫 페이지로 만든 과거 캐시는 원본을 보존하고 전체 조회 대상으로 갱신하며, 완성된 시세는 24시간 재사용한다.

`book_complete`, `coverage_version=2`, 전체 범위에 필요한 고유 관측 수를 충족한 근거만 최고 상태 시세와 예상 가격에 사용한다. 네이티브 실행 측에서도 이 조건을 확인한다. 신규종의 비교 대상은 각 상품의 전체 상태 수집이 완료되거나 실제 판매 수량 0건임을 확인한 뒤에 계산한다. 전체 조회가 끝나기 전의 20원 등 부분 시세로 합성을 허용하거나 자동 잠금을 걸지 않는다. 공지 수집과 일반 교배·재고 검증은 페이지 수집과 별개로 진행한다.

0.4.23은 신규종의 비교 시세를 보유 재고 밖에서도 수집한다. 예를 들어 Bloodmoon Mola 3성은 같은 희귀도·별 등급의 기존 일반종인 Coral Clownfish·Golden Seahorse·Golden Moorish Idol·Sunburst Ranchu 3성의 상품을 조회한다. 실제 캐시는 상품별 24시간 재사용하며, 조회는 기존 단일 Chrome 작업과 전역 간격·백오프를 따른다. 시즌 한정종은 희소성 조건이 달라 일반종의 예상 가격 비교에서 제외한다.

공식 시즌 안내는 Steam 공개 News API에서 읽는다. `season-discovery.json`에는 게임의 현재 어종 표 기준선과 이후 추가된 ID를, `season-evidence.json`에는 공식 공지의 시즌 번호·발행일·본문 해시·추가 어종 수와 확인한 이름을 보관한다. 공지에 이름이 이미지로만 있는 경우에는 게임의 영문 어종명과 ID를 사용하고 이름 출처를 구분한다. 장터 정보가 없다는 사실만으로 신규종이라고 판정하지 않는다. 공식 공지의 추가 수량과 어종 표 변경이 일치한 신규 일반종만 예상 가격 대상으로 등록한다. 현재 설치의 시즌 2 첫 기준선은 이미 확인된 8종과 공식 공지를 명시적으로 연결한다.

새 시즌에서는 저장한 어종 표와 새 표를 비교하고 해당 시즌의 공식 안내를 대조한다. 확인된 공지는 24시간 캐시하고 시즌이 바뀌면 다시 확인한다. 공지 수집 실패는 1시간 후 재시도하며 기존 교배·합성을 전역 중단하지 않는다. 공지 내용은 근거 자료로만 처리하고 포함된 명령이나 외부 링크를 실행하지 않는다. RPA·Codex CLI·사용자 Steam 로그인 정보는 사용하지 않는다. 네이티브 실행 측도 현재 시즌 번호, 공식 Steam 앱 경로와 공지 ID, 어종 표의 이름·시즌종 여부를 확인한다. 향후 게임 바이너리 변경에 대한 기존 빌드 검증은 별도이다.

0.4.22는 시즌 2 신규 일반종 5종(FS00036·37·41·42·43)의 실측 장터 매물이 없을 때 예상 가치를 사용한다. 게임의 현재 CSV에서 어종·희귀도·별 등급·영문 장터명을 읽고, 같은 희귀도와 별 등급인 기존 일반종의 유효한 24시간 시세를 비교한다. 각 비교종의 실제 관측된 최고 잔여 교배 횟수에 해당하는 판매자 최고 호가를 구한 뒤, 비교종 전체 중 가장 높은 금액을 예상 가치로 사용한다. 이 값이 1,000원 이하이면 교배·일반 합성에 사용할 수 있다. 신규종끼리 또는 시즌종의 가격을 서로 추정 근거로 쓰지 않으며, 비교 시세가 없는 등급은 금액을 만들지 않고 대기 사유를 표시한다.

예상 가격은 `estimated_peer_max`로 구분하고 실측 가격 필드는 비워 둔다. 실측 매물이 생기면 기존 시세 정책이 우선한다. 예상 가격이 높으면 보존하되 영구적인 게임 잠금을 자동으로 걸지는 않는다. 사용자 잠금·수동 예약·시즌 재료와 어종별 1~5성 수집 목표는 그대로 적용한다. 신규종의 장터 등록 여부는 상품별 24시간에 한 번 확인하며, 기존 전역 요청 간격과 백오프도 유지한다. Python 판단 외에 네이티브 실행 측에서도 게임 CSV와 비교종 가격 근거를 다시 대조한다. 근거: [시즌 2 공식 공지](https://store.steampowered.com/news/app/4842670/view/710038327520139217).

설치 대상: Steam build 26315872 / PC FISH 1.6.2 / Unity 6000.0.76f1 / Windows x64 IL2CPP.

실제 마우스·키보드 입력, 포커스 전환, 화면 인식 없이 게임 내부 상태를 읽는다. 교배는 원래 `UIBreed.Breed`를 호출하고, 합성·시즌 제작은 기존 `NetworkManager.FishMerge` / `FishCraft`를 호출한다. 게임 서버 요청과 결과 반영은 게임의 기존 구현이 담당한다. 모드는 결과를 만들거나 하트·교배 횟수·대기시간을 늘리지 않는다. 백그라운드로 실행 중인 게임에서 작동하며 게임을 종료하면 진행하지 않는다.

## 원래 게임 순서의 교배

0.4.21의 서버 미반영 처리 순서는 `원래 교배 성공·저장 → 최소 60초 후 UID 조회 → 없으면 원래 ManageRestore 성공 콜백으로 서버 데이터 복구 → 재고·기본종·기존 잠금·하트 보존 검증 → 기존 pending 보관 → 새 요청 ID로 교배`다. 조회에 사용한 바로 그 응답의 원래 복구 콜백을 실행하므로 복구를 위해 두 번째 GET을 추가하지 않는다. 복구는 서버에 없는 결과 개체를 로컬에서 제거할 수 있으며, 적용 전 원본 복구 기록을 별도 보존한다. 무관한 서버 물고기의 소실이나 기존 잠금 해제는 정상 미반영 복구로 취급하지 않는다.

복구 완료 후에는 기존 최소 작업 간격을 지키고, 기본종은 마지막 재고 조회로부터 60초 간격도 지킨다. 새 교배를 우선 계획하되 기존 잠금·시세·부모 상태·시즌 보호는 다시 검증한다. 연속해서 같은 복구가 발생하면 대기는 30/60/120/240/300초로 증가하고 정상 서버 확인 후 초기화된다. 원래 유료 교배 요청이나 성공 콜백을 재전송하지 않는다.

모드는 하트 회복 기준 시각을 직접 대입하지 않는다. 재접속·옛 별도 추적 복구에서도 경험치 보충이나 하트 차감을 따로 수행하지 않고 원래 데이터 복구의 결과를 사용한다. 새 교배의 경험치·하트·부모 사용 횟수·저장은 원래 `UIBreed.Breed`와 원래 성공 핸들러가 처리한다. 진단·복구 체크포인트는 BepInEx 아래 자체 JSON에 저장하며 게임의 `.es3` 파일을 직접 덮어쓰지 않는다. 아래 버전별 검증 기록은 해당 시점의 과거 동작과 증거다.

0.4.20의 새 교배는 원래 `UIBreed.Breed` → `FishBreed` → 원래 성공 콜백 → `NewFish`·부모 갱신·저장 → 원래 UI 성공 핸들러의 경험치·하트 차감·저장 순서로 실행한다. 유효한 성공 콜백을 재고 조회까지 보류하지 않고, 모드의 관리 콜백에서 비용을 중복 적용하지 않는다. 기본종은 서버에서 소모되는 교배 횟수가 없으므로 매 교배 직전의 소유 조회를 생략한다. 다른 재고 조회가 끝난 직후에도 기본종 교배는 60초 간격을 둔다. 일반 부모의 서버 소유 확인과 모든 실행 직전 보호 조건은 유지한다.

실제 원래 저장을 관측한 뒤 최소 60초가 지나면 읽기 전용 조회로 새 UID와 기존 재고를 대조한다. 새 결과가 확인되기 전에는 다음 소비 요청을 보내지 않는다. 자연 하트 회복·경험치·성장·보상은 실패로 보지 않으며, 하트 1회 차감·선택한 일반 부모의 횟수 1회 감소·기존 개체와 잠금 보존을 검증한다. 이미 비용을 저장한 새 교배가 서버에 반복해서 없으면 `pending`을 유지한다. 로컬 반영 전·무소비 조건의 과거 `deferred-receipts` 예외로 넘기지 않는다.

`native-breed-events`에는 원래 성공 콜백 진입, 원래 하트 저장, 콜백 반환, 지연 재고 조회를 기록한다. `status.json`의 `native_breed_flow`, `native_completed_at`, `native_next_verification_at`으로 실제 소비 요청 응답 대기와 저장 후 확인 대기를 구분한다. 잘못된/이미 보유한 새 UID, 중복·다른 요청의 지연 응답, 불명확한 회계 체크포인트는 기존과 같이 보존·중단한다. 과거 미반영 요청은 재전송하거나 새 경로로 다시 적용하지 않는다.

직접 비교는 계정에 묶인 `native-comparison.json`으로 횟수와 유효기간을 제한하며 기본종 두 마리만 사용한다. 비교 중에는 일반 자동화의 추가 게임 재고 조회와 다른 소비 행동을 쉬고, 원래 저장 뒤에만 조회한다. 비교 원본은 `native-comparison-events`와 기존 원장에 유지하며 관측 시점을 바꾼 비교 자료는 일반 계획 학습에서 제외한다. 비교의 성공은 원래 경로의 실행 증거이며, 적은 표본만으로 간헐적 미반영의 단독 원인이나 영구 해결을 입증하지는 않는다.

하트 예상 시각은 Unix `long` 시각과 게임의 `float` 간격을 **double로 변환한 뒤** 더한다. 변환 전 `long + float` 계산은 현재 시각에서 약 128초 단위로 반올림돼 충전 시각을 잘못 예측할 수 있었다. 실제 게임 하트나 저장 시각은 수정하지 않는다.

## 서버 재고 동기화와 거절 원인

0.4.17은 사용자의 실제 매물 기준을 반영한다. `best_observed_breeds`는 같은 어종·현재 별 등급에서 조회된 실매물 중 남은 교배 횟수가 가장 큰 상태를 고르고, 그 상태 매물들의 최고 판매자 호가가 1,000원 이하이면 일반 합성·시즌 제작 재료로 허용한다. 이론상 만교배 매물을 요구하지 않는다. 모든 관측 매물이 소진 상태라면 0회가 관측 최고 상태가 된다. 잠금·수동 예약·시즌 수량 보호와 24시간 캐시의 원래 유효기간은 유지한다. 상품 설명 부재와 잘못된 응답을 구분해 기록하며, 조회된 매물 수·전체 매물 수를 기록해 관측 범위를 표시한다.

0.4.16은 **미반영 성공 응답의 원인 조사에 필요한 기록을 보강한 버전**이다. 미반영 자체를 고쳤다는 의미는 아니다. 기존 5건은 쓰기·읽기 인증 토큰 해시가 같고, 반환 UID 재사용이나 서버 목록에서의 대소문자·GUID 표기 차이도 없었다. 원래 성공 콜백 처리에는 결과를 서버에 등록하는 별도 후속 호출이 없으며, 확인 후 저장하기 전 버전에서도 로컬 저장 후 서버에서 발견되지 않은 물고기 기록이 있다. 이 근거만으로 서버 내부 저장 실패의 원인을 확정하지 않는다.

성공 응답에서는 네이티브 `NewFish`가 실제 읽는 `fish`, `type`, `grade`, `level`, `growth`, `breedCount`, `breedMaxCount`, `breedDate`, `breedNextDate`, `timestamp`의 검증된 스칼라 값만 `network-responses`에 추가한다. 알 수 없는 필드·토큰·응답 원문은 저장하지 않는다. `http-completions`는 기존 SDK 코루틴의 완료를 관측해 HTTP 상태·결과·응답 해시를 기록하며, 요청·콜백·본문·헤더를 바꾸거나 추가 조회하지 않는다. 이 빌드에서 읽을 수 없는 응답 헤더는 미확인으로 명시한다. 선택적 HTTP 관측 실패는 기존 요청 진행과 분리한다. 기존 미확정·별도 추적 원본, 요청 간격과 보호 조건은 유지한다.

0.4.15는 미반영 요청을 별도 추적으로 넘긴 뒤에도 해당 요청이 켠 통신 중 UI 상태가 남는 문제를 수정한다. 2026-11-08 06:03:16에 요청 기록은 정상 분리됐지만 진행 중 요청 없이 `network_busy`가 유지돼 이후 자동화가 대기한 사례를 확인했다. 자동화가 소비 요청을 시작할 때 그 요청 번호와 이전 처리·표시 상태를 기억하고, 정상 완료·무소비 거절·별도 추적 전환 시 해당 요청이 소유한 UI 상태를 한 번만 복원한다. 다른 요청 번호나 재시작 전 요청 번호로 현재 UI를 해제하지 않으며, 진행 중인 실제 통신을 시간만 보고 무시하지 않는다. `network_ui_owner`, `ui_is_processing`, `network_indicator_visible`과 `network-ui-release-events`에 소유·해제 근거를 남긴다.

0.4.13에서 시작한 기본종 미반영 요청의 별도 추적을 0.4.14에서 보강했다. 성공 응답의 UID가 서버에 나타나지 않아도 전체 자동화를 무기한 막지 않는다. 기본종 두 마리의 교배이고 로컬 반영·비용 처리가 시작되지 않았으며, 하트·전체 물고기·교배 횟수·잠금의 소비가 없고 서버 재고도 요청 전과 같을 때만 적용한다. 요청 후 60초 이상 지나고, 30초 이상 간격의 성공 조회 3건 이상이 60초 이상 같은 상태를 확인해야 한다. 이전 조회 근거도 계정·시각·로컬 ID 일치를 확인해 사용하며, 재개 직전 새 조회로 다시 확인한다. 일반 부모의 교배, 합성·제작, 실제 자원 변화에는 이 예외를 적용하지 않는다.

확인된 기본종 미반영 요청은 실패나 성공으로 꾸며 기록하지 않고 `deferred-receipts`로 옮겨 별도 추적한다. 원래 `pending.json`은 `resolved-pending`에 보존하고 새 요청 번호로 정상 자동화를 재개한다. 이전 소비 요청을 다시 전송하지 않는다. 결과 UID를 로컬에 임의 생성하거나, 없는 결과에 하트 비용을 차감하지 않는다.

최근 미반영된 정확한 부모 쌍은 별도 추적 전환 시각부터 10분 동안 건너뛰고 다른 조합을 선택한다. 해당 쌍의 후속 교배가 정상 완료되면 대기를 해제한다. 개별 물고기를 영구 제외하지 않는다. 이 기록을 명시적 거절이나 확률 학습의 실패 사례로 바꾸지 않는다.

이전 결과가 나중에 서버에 나타나면 원래 계정과 실제 소유를 확인한 뒤 기존 게임 복원으로 결과를 받아오고 하트 비용을 한 번만 반영한다. 비용 체크포인트는 재시작에도 유지한다. 이 확인은 보통 재고 조회에 함께 수행하고 별도 조회는 5분 간격으로 제한한다. `late-receipt-events`와 `settled-deferred-receipts`에 정산을 기록한다. `status.json`의 `deferred_receipts`는 별도 추적 중인 수, `deferred_receipt_note`는 그 처리 상태다. 0.4.12의 30초 작업·120초 시세·조회 간격과 잠금·시즌·시세 보호는 유지한다.

0.4.12는 실제 요청 기록에서 발견한 재고 확인 폭주와 복구 중단을 고친다. 미확정 교배 뒤 60초 동안 성공한 읽기 조회가 30건 있었고, 전체 기록의 최고치는 60초에 31건이었다. 이는 게임 API의 GET 호출 기록이며 Steam 내부 요청 전체를 뜻하지 않는다. 과거 브라우저 조회는 상품별 마지막 시각만 남아 있어 총 HTTP 요청 수를 복원할 수 없다. 따라서 이 조회 빈도가 Steam의 HTTP 429를 직접 일으켰다고 확정하지는 않는다.

설치 설정의 일반 교배·합성·제작 최소 간격은 30초, 장터 브라우저 조회 간격은 120초다. 모든 자동 재고 조회는 하나의 15초 최소 간격을 공유하고, 같은 계정의 60초 이내 서버 소유 확인이 현재 로컬 ID를 모두 포함하면 실행 전 중복 GET을 생략한다. 결과 미반영·연결 실패 시 읽기 재조회 간격은 30→60→120→240→300초로 늘어난다. 마지막 대기 시각과 실패 횟수는 디스크에 남겨 재시작으로 조회가 몰리지 않게 한다.

60초 경과 자체로 결과 확인을 영구 중단하지 않는다. 미확정 요청이 있으면 그 요청의 원래 계정·성공 UID·재료 변화를 먼저 읽기 조회로 확인한다. 재시작으로 네이티브 콜백이 사라졌을 때도 확인한 **같은 GET의** 기존 복원 처리를 사용해 결과를 반영한다. 하트 비용은 기록된 단계 사이에서 한 번만 저장하고, 서버 복원으로 이미 반영된 경험치는 중복 지급하지 않는다. 요청 번호와 복구 단계는 `receipt-recovery`에, 확인·완료는 `recovery-events`와 `resolved-pending`에 남긴다. 소비 요청을 재전송하지 않으며, 성공 결과 또는 명시적 무소비 거절이 확인되면 자동화를 재개한다. 성공 UID가 여전히 서버에 없거나 실제 손실·잠금 해제·비용 저장 도중의 중단이 확인되면 원본 기록을 유지한다.

미확정 소비 결과를 확인하는 동안 장터의 새 조회는 쉬고 기존 24시간 캐시는 계속 사용한다. HTTP 403/429는 문서뿐 아니라 Steam의 하위 API 응답에서도 검사하며, `Retry-After`를 존중하고 반복 제한은 1→2→4→6시간 대기한다. 이 시각도 재시작에 보존한다. 시세 브라우저는 이미지를 다운로드하지 않는다. `network-checks`에는 실제 재고 요청 시작을, `market-requests`에는 브라우저 조회 시작·종료와 관측한 HTTP 응답 수를 기록한다. 브라우저의 관측 응답 수는 종료 후 늦게 도착한 요청까지 포함하는 전체 패킷 수는 아니다.

0.4.11은 자동화 요청의 처리 순서를 변경한다. 요청 직전에 선택한 일반 물고기 ID가 서버에 있는지 읽기 전용 조회로 확인한다. 서버의 성공 응답은 즉시 로컬에 반영하지 않고, 새 UID의 서버 소유와 합성·제작 재료의 서버 제거를 확인한 뒤 기존 게임 콜백을 한 번만 실행한다. 확인 전에는 `NewFish`와 그 개체의 로컬 저장이 실행되지 않는다. `receipt-confirmations`에는 로컬 반영보다 먼저 서버 확인 근거를 남긴다. 서버에서 확인되지 않은 성공 응답은 같은 소비 요청을 재전송하지 않고 읽기 조회로 확인한다.

콜백은 네이티브 콜백 대상과 원래 요청 번호에 연결한다. 완료된 새 UID의 중복 응답과 다른 요청에 늦게 도착한 응답은 기존 게임의 재고 변경 코드에 들어가기 전에 차단한다. 이 검사가 로컬 변경 뒤에 있던 이전 구조에서는 늦은 콜백이 재고를 먼저 바꾸고 모드에서 뒤늦게 무시될 수 있었다. 계정 문맥이 바뀌면 이전 재고 판정을 재사용하지 않으며, 계정 변경 도중 도착한 재고 복원 응답도 적용하지 않는다. 같은 계정의 토큰 갱신은 계정 변경으로 취급하지 않는다.

읽기 전용 조회도 각각의 요청·계정 문맥에 연결하고 한 번만 완료한다. 이전 조회의 지연·중복 응답은 다음 조회나 소비 요청의 확인으로 사용할 수 없다. 조회만 15초 제한을 넘으면 해당 조회를 종료하며, 이미 보낸 소비 요청은 재전송하지 않는다. 필수 콜백 연결 패치가 설치되지 않은 경우에는 소비를 실행하지 않고 `unsupported_bindings`로 원인을 표시한다. 정상 작동 중 선택적 진단 파일 기록 실패는 거래 검증과 분리한다.

생성 응답 UID·서버 확인·최초 로컬 저장·불러오기를 연결하는 기록을 추가했다. `response-callback-events`, `persistence-events`, `inventory-probes`로 재발 시 최초 불일치 단계와 중복·지연 콜백을 구분한다. 진단용 서버 조회는 게임의 SDK와 인증 문맥을 사용하되 로컬 복원 콜백을 실행하지 않아 재고를 정리하거나 삭제하지 않는다. 인증 토큰 원문과 서버 응답 원문은 저장하지 않으며 비교용 문맥 해시만 기록한다.

과거 누락된 UID의 최초 생성 응답 ID와 전체 콜백 이력은 이전 로그에 없었다. 따라서 과거 불일치의 발생 주체를 저장 파일 덮어쓰기·중복 콜백·다른 실행기·서버 저장 문제 중 하나로 확정하지 않는다. 0.4.11은 서버 소유 확인 전 로컬 확정과 늦은 콜백의 재적용이라는 모드의 재발 경로를 차단한다. 검증에서는 이 순서와 단일 적용을 별도로 확인한다.

사용자는 같은 계정으로 다른 PC에서 실행하지 않는다고 확인했다. 조사한 Steam Cloud 로그에서도 해당 시간대 저장 파일 다운로드·롤백은 관찰되지 않았다. 이는 그 두 원인을 뒷받침하는 근거가 없다는 의미이며, 과거 누락의 서버 측 원인을 확정하는 증거는 아니다.

0.4.9는 자동화를 시작하기 전에 게임의 `NetworkManager.ManageRestore`로 서버 재고를 대조한다. 이 경로는 기존 게임의 GET 조회와 로컬 복원 처리이며, 교배·합성·거래나 하트 소비를 하지 않는다. 서버에 없는 오래된 로컬 개체 기록을 제거하고 서버에만 있는 물고기를 복구하며, 서버의 남은 교배 횟수와 준비 시각을 반영한다. 서버에 있는 개체와 기본종의 보존, 기존 잠금 보존, 서버 ID 집합과 동기화 결과의 일치를 확인한 뒤 자동화를 진행한다. 시즌 예약도 이 실제 재고로 다시 계산한다. 수조·장식 등의 설정 초기화 함수는 호출하지 않는다.

실제 거절 응답 `Missing fishIds`는 요청 필드 누락처럼 보일 수 있지만, 조사한 요청은 `parentFishId`에 선택한 10개 ID가 정확히 있었다. 서버는 그중 서버 재고에 없는 ID들을 지목했다. 최초 대조에서 로컬에만 있던 5개 기록과 서버에만 있던 1마리를 확인했다. 교배·합성에서 이 응답을 다시 받으면 다른 부모를 반복 시도하기 전에 서버 재고를 다시 동기화한다. 서버 조회 실패 시에는 재조회하고, 확정된 서버 재고를 얻기 전에 새 소비 요청을 보내지 않는다.

`network-requests`에는 요청 종류와 ID 배열의 형태·일치 여부를 기록한다. `network-responses`에는 상태·정제된 오류·반환 UID와 0.4.16의 검증된 물고기 스칼라 필드만 기록한다. 관측 코드는 원래 요청 본문·주소·인증 헤더를 변경하지 않는다. 인증 정보나 응답 원문 전체를 저장하지 않는다. `inventory-sync-events`는 서버 ID 집합과 동기화 전후 로컬 상태를 보관하며, 일반 교배·합성 학습 이벤트와 분리한다. 동기화는 소비 요청의 `pending.json`과 다른 읽기 작업 기록을 사용한다.

0.4.5부터 명시적인 `Fail` 응답에서 새 결과 개체가 없고 전체 인벤토리·교배 횟수·하트·잠금에 소비가 없음을 확인하면 `rejected-events`에 기록하고 재계획한다. 0.4.6은 이 거절 뒤에도 설정된 기본 작업 간격(현재 10초)을 적용해 다른 작업을 60초씩 막지 않는다. Protected 모드는 거절된 정확한 합성 조합과 교배 부모 쌍을 10분간 건너뛴다. 합성은 겹침이 적은 다른 조합을 우선하고, 교배는 같은 능력치의 다른 개체도 후보로 검토한다. 개별 물고기를 영구 보호하지 않으며 다른 합성·교배를 계속한다. 이런 요청 거절은 전체 자동화를 정지시키지 않는다. 타임아웃·네트워크 오류 또는 소비가 관찰되는 응답은 미확인 기록을 유지한다. 거절 기록은 성공 이벤트나 확률 학습에 넣지 않는다.

Protected 모드에서는 하트가 5개이면 현재 가능한 교배를 일반 합성이나 더 좋은 부모의 미래 준비 시각보다 먼저 처리해 회복 타이머를 다시 가동한다. 최근 10분 내 합성 거절이 있으면 하트가 1~4개일 때도 즉시 가능한 교배를 다른 합성보다 먼저 처리해 반복 거절이 교배를 밀어내지 않게 한다. 교배가 비활성화됐거나 인벤토리가 가득 찼거나 사용할 부모 쌍이 없으면 합성을 판단한다. 완성된 시즌 레시피의 제작 우선순위와 잠금·수동 예약·시세 보호는 유지한다.

## 시즌 재료 자동 보존과 제작

0.4.0의 `auto_season_craft=true`는 게임이 로드한 현재 시즌 레시피를 읽고 목표까지 필요한 재료 수량을 자동 예약한다. 0.4.3부터 예약 개체는 일반 합성에서 보호하면서 교배에는 사용할 수 있다. 교배는 부모를 없애지 않으므로 레시피 수량을 유지하며, 잠금·수동 예약·시세/등급 보호는 별도로 검사한다. 재료가 완성된 시즌 레시피는 일반 작업보다 먼저 실행한다. 현재 설정과 새 설치 템플릿의 목표는 시즌 어종별 1~5성 각각 1마리다. 수집용 개체를 보존하면서 제작용 중간 개체를 추가로 확보한다. 현재 설치에는 활성화했으며, 기존 설정 파일에 필드가 없으면 호환성을 위해 비활성으로 유지한다. [실제 레시피, 목표 설정과 보호 정책](season-crafting.md)을 참고한다.

```powershell
& 'C:\Project\PC-fish\scripts\Set-Automation.ps1' -SeasonCrafting On -SeasonGoal Collection
```

게임의 시즌 기간이 끝나면 제작과 일반 재료 자동 예약을 중단한다. 현재 시즌 레시피를 확인하지 못하면 교배·합성을 포함한 물고기 소비를 보류한다. 잠금·수동 예약·일반 재료의 시세 보호는 시즌 제작에서도 지키며, 같은 시즌의 이전 등급 시즌 물고기만 정확한 상위 레시피의 재료로 허용한다. 제작 결과는 `craft-events`에 따로 기록하고 일반 교배·합성의 확률 학습에 넣지 않는다.

0.2.2에서는 자동 교배 후 수조 바깥 하트 표시가 사용 전 수치로 남던 갱신 누락을 수정했다. 일반 교배 성공 처리가 호출하는 `GameManager.CheckTankShowPopup`을 하트 소비·저장 후 호출한다. 이 함수가 `UIBreedTankPopup.CheckBreedCount`로 각 하트의 그림을 실제 남은 수에 맞추고, 하트가 없을 때의 표시도 정상 처리한다. 자연 회복·수조 레벨·경험치가 바뀔 때도 갱신하며 실제 하트 수는 변경하지 않는다. `status.json`의 `heart_indicator_synced_to`는 마지막으로 정상 표시 갱신을 마친 하트 데이터 값이다.

## Steam 장터 가격에 따른 자동 잠금

0.4.17의 현재 설정은 `market_merge_price_basis=best_observed_breeds`다. 합성과 시즌 제작은 **실제로 조회된 같은 어종·별 등급에서 남은 교배 횟수가 가장 많은 상태**의 가치로 판단한다. 그 상태에 해당하는 매물들 중 최고 판매자 호가가 **1,000원 이하**이면 현재 재료의 잔여 횟수와 무관하게 허용한다. 같은 잔여 횟수라면 최대 횟수가 달라도 함께 비교한다. 실제 최고 상태가 `1/2`이면 그 매물 가격을 쓰고, 모두 소진된 매물만 있으면 그 매물들의 가격을 쓴다. 만교배 매물·최근 거래 수·현재 개체와 정확히 같은 횟수 매물은 요구하지 않는다. 관측 범위의 시세이며 장터 전체를 확인했다는 의미는 아니다. 이전 `full_breeds` 정책은 명시적으로 선택할 때만 유지한다.

```powershell
& 'C:\Project\PC-fish\scripts\Set-Automation.ps1' -MergePriceBasis BestObservedBreeds
# 이전 현재 개체 교배 횟수별 기준:
& 'C:\Project\PC-fish\scripts\Set-Automation.ps1' -MergePriceBasis ExactBreeds
```

좋은 상태의 가치가 1,000원 이하로 확인된 상품은 현재 호가가 1,000원이라는 이유로 자동 잠그지 않는다. 사용자 잠금·수동 예약·시즌 필요 수량은 유지한다. 실제 가격이 누락·만료됐거나 유효한 매물이 하나도 없는 상품은 판단을 기다리고 다른 상품의 처리는 계속한다. 아래 현재 개체 기준과 매물 일치/최근 체결 요건은 교배 및 `exact_breeds` 정책에 적용하며, `best_observed_breeds` 합성에는 위 기준을 적용한다.

0.3.0의 `protection_mode=market`은 별 등급의 일괄 제외를 시세 확인으로 대체한다. 새 설치 템플릿의 기준은 사용자가 지정한 **수수료 후 1,000원 이상**이다. 기존 설정에 이 필드가 없으면 이전 `grade` 정책을 유지하며 업그레이드만으로 실행 중 정책을 바꾸지 않는다.

```powershell
& 'C:\Project\PC-fish\scripts\Set-Automation.ps1' -Mode Protected -Protection Market -MarketMinimumKrw 1000
# 기존 별 등급 기준으로 전환:
& 'C:\Project\PC-fish\scripts\Set-Automation.ps1' -Mode Protected -Protection Grade
```

시세 보호에서는 새로 얻은 개체와 기존 보유 개체를 같은 방식으로 검사한다. 게임의 영문 어종명·별 등급으로 장터 상품을 찾고, **남은 교배 횟수와 최대 교배 횟수**가 모두 일치하는 매물을 대조한다. 기본종은 장터 조회 대상에서 제외하며 기존 성숙·교배 조건을 그대로 적용한다.

| 상태 | 처리 |
| --- | --- |
| `pending` | 조회 전·실패·만료·조건 불일치·판단 자료 부족. 교배·합성에서 임시 제외 |
| `keep` | 판매자 호가 기준 1,000원 이상. 즉시 후보에서 제외하고 안전한 다음 틱에 게임의 잠금을 적용 |
| `release` | 기준 미만이고 매물 표본·최근 거래 조건 충족. 다른 보호 및 교배·합성 조건을 검사한 뒤 후보에 포함 |

매물의 `unPrice`를 원 단위로 변환해 판매자 수령 기준 호가로 사용한다. 구매자 총액에서 임의의 수수료율을 빼지 않는다. 일부 저가 매물 하나 때문에 보존 가치가 낮다고 판단하지 않도록, 같은 교배 횟수 매물 중 **세 번째로 낮은 판매자 호가**를 사용한다. 일치 매물이 1~2개뿐이면 그중 높은 호가를 사용한다. 기준 미만으로 해제하려면 전체 매물이 관찰되었거나 일치 매물이 최소 3개 있어야 하며, 상품의 최근 30일 체결 기록도 있어야 한다. 정확히 1,000원은 보존한다. Grade 5도 이 조건을 충족하면 후보가 될 수 있다.

이 값은 현재 판매자의 희망가다. 최근 체결량은 상품 전체 기준이며, 해당 개체의 판매 확률·잔여 횟수별 체결가를 보장하지 않는다. 숨겨진 외형 속성의 가격 프리미엄은 평가하지 않는다. 시즌 어종·예약 ID/어종·사용자 잠금은 계속 보호한다. 잠근 개체는 가격이 내려가거나 정책을 바꿔도 자동 해제하지 않는다.

조회는 Selenium이 독립된 임시 프로필의 Google Chrome을 headless 모드로 실행해 공개 장터 페이지를 읽는다. 로그인·개인 계정 쿠키·API 키는 사용하지 않는다. 매번 조회를 마치거나 실패하면 그 조회의 크롬과 드라이버를 닫는다. 초기 `valve-ssr-data` 또는 렌더링 뒤 `window.SSR`로 옮겨진 공개 장터 쿼리 자료만 읽으며, 계정 설정이나 세션 정보는 가져오지 않는다. 기존 단순 HTTP 방식으로 자동 전환하지 않는다.

Python의 별도 스레드에서 한 번에 한 상품만 조회하므로 게임 메인 스레드와 계획 루프를 크롬 응답 대기로 막지 않는다. 같은 어종·별 등급의 개체들은 캐시를 공유하며 **24시간 이내에 수집한 자료가 있으면 크롬을 실행하거나 재조회하지 않는다.** 새 물고기나 교배 횟수 변경도 기존 자료로 재평가한다. 일치 매물이 없으면 임시 보호한다. 기본 시세 유효기간은 24시간(`market_quote_ttl_seconds=86400`)이며, 24시간이 지난 상품이나 시세가 없는 상품을 조회할 때만 최소 30초 간격을 적용한다. 403/429 또는 추가 확인 요구에서는 전체 조회를 1시간, 크롬 연결 오류 등에서는 15분 대기한다. 상품별 자료 부족·404에서는 해당 상품만 15분 대기하고 다른 상품은 계속 확인한다. 재시작에도 전체·상품별 대기 시각을 보존한다. Steam의 제한 또는 페이지 구조 변경으로 가격을 계속 확인하지 못하면 미확인 개체의 보호가 계속된다.

게임 쪽은 보고서의 세션·설정 해시, 개체 ID·어종·외형·등급·교배 횟수, 원화 통화와 유효기간을 다시 대조해 상태를 계산한다. Python이 기록한 `release` 문자열만으로 소비를 허용하지 않는다. 교배로 횟수가 바뀌면 기존 가격 근거도 다시 대조한다. 잠금은 현재 잠기지 않은 물고기에만 정상 게임 함수 `FishUtil.Lock`을 호출한다. 이 함수가 토글임을 확인했으므로 이미 잠긴 물고기에는 호출하지 않는다. 실제 메뉴 조작·요청 진행·불명확한 결과·Pause/Observe 중에는 자동 잠금을 수행하지 않는다.

가격 판단과 캐시는 `market-review.json`, `market-cache.json`에, 적용한 잠금은 `market-lock-events/*.json`에 기록한다. 확률 학습의 교배·합성 이벤트와 섞지 않는다. 장터 등록·판매·구매는 수행하지 않는다.

## 자동 수조 레벨업

`auto_level_up=true`가 기본이며, 자동화가 켜진 Protected/Economic 모드에서 함께 실행된다. 실제 수조의 누적 경험치가 다음 레벨의 기준에 도달하면 게임의 `IsCheckTankLevelUp`으로 다시 확인하고 `UpgradeTankLevel`을 한 번 호출한다. 이 게임은 누적 경험치를 사용하므로 레벨업 때문에 경험치를 임의로 빼거나 더하지 않는다.

기존 내부 함수가 수조 크기·배치 한도, 해당 레벨의 물고기·장식 보상과 업적 갱신을 처리한다. 모드는 결과가 정확히 1레벨 상승했는지 확인하고 저장한 뒤 일반 상태를 갱신한다. 경험치가 여러 단계의 기준을 충족하면 순서대로 한 단계씩 진행하며 최고 레벨에서는 멈춘다. 보상 안내 창을 새로 띄우지 않는다. 이미 열려 있는 레벨업 완료 팝업은 그 팝업의 정상 `Ok` 함수를 호출해 닫는다.

0.4.2는 레벨업의 성공을 실제 레벨 상승으로 판단한다. 경험치 차이, 먹이 성장, 보상의 표시 시점·수량·성숙도, 배치 상태가 모드의 예상과 다르다는 사실은 오류나 중단 사유로 삼지 않는다. 레벨 변화가 관찰되지 않으면 자동 레벨업만 보류하고 그 시도를 반복하지 않는다. 기존 물고기가 사라지거나, 일반 물고기의 교배 횟수가 의도치 않게 소비되거나, 사용자 잠금이 풀리거나, 레벨업 도중 하트가 소비된 경우에는 실제 손실 근거로 보고 전체 소비를 중단한다.

자동 레벨업은 교배·합성·시즌 제작의 통신 요청 상태와 별도로 관리한다. 레벨업 처리나 보상 창 닫기에서 예외가 생겨도 레벨업만 보류하며, 인벤토리를 새로 읽은 다음 일반 자동화를 이어간다. 이전 레벨업의 미완료 기록이 남은 재시작도 자동 레벨업만 보류한다. 하트 표시·수조 화면 갱신 실패는 데이터 오류로 분류하지 않고 표시 갱신을 다시 시도한다. 시세 자동 잠금 실패는 60초 후 재시도하며 그동안에도 해당 고가 개체의 소비 제외는 유지한다. 추천을 만든 뒤 물고기 준비 상태나 보호 조건이 달라진 경우에는 명령을 버리고 다시 계획하며 오류로 표시하지 않는다.

교배·합성 등 다른 요청이 진행 중이거나 미확인 결과가 있으면 실행하지 않는다. 홈의 수조 정보 패널이 열려 있어도 레벨업은 처리하지만, 다른 메뉴·일반 확인창·네트워크 처리 중에는 기다린다. Pause/Observe에서는 레벨업과 팝업 닫기도 실행하지 않는다. `auto_level_up=false`로 레벨업만 따로 끌 수 있다.

레벨업 직전에는 `level-up-pending.json`, 완료 후에는 `level-events/*.json`을 남긴다. 완료 기록의 `exp_change`와 `added_fish_ids`는 관찰값이며, 예측값과의 일치를 실행 조건으로 요구하지 않는다. 미완료 레벨업은 중복 보상을 피하려고 자동 재시도하지 않지만 교배·합성은 계속할 수 있다. 이 기록은 교배 확률 학습 자료와 별도로 보관한다.

## 켜기·끄기·상태

Windows 시작으로 게임이 실행될 때도 `게임 실행 → BepInEx 모드 로드 → 저장된 자동화 설정 읽기 → 계획기 자동 시작` 순서로 작동한다. Codex 앱이나 PowerShell 명령을 매번 실행할 필요가 없다. 별도의 Windows 시작 항목이나 작업 스케줄러 작업을 추가하지 않는다. 현재 설치 설정과 새 설치 템플릿은 `enabled=true`, `mode=protected`로 맞췄다. 게임 초기 로딩이 끝나면 실제 상태를 읽고 교배·합성 또는 대기를 결정한다.

사용자가 `Pause` 또는 `Observe`로 저장한 경우에는 그 선택도 다음 실행에 유지된다. 이전 교배·합성·시즌 제작 요청의 결과가 불명확한 기록이 남아 있으면 중복 소비를 막기 위해 소비 작업을 보류한다. 레벨업 기록은 해당 기능만 보류한다.

게임을 실행한 상태에서 PowerShell로 실행한다. 재시작 없이 설정이 반영된다.

```powershell
& 'C:\Project\PC-fish\scripts\Set-Automation.ps1' -Mode Protected
& 'C:\Project\PC-fish\scripts\Set-Automation.ps1' -Mode Pause
& 'C:\Project\PC-fish\scripts\Set-Automation.ps1' -Mode Status
```

`Pause`는 새 작업을 막는다. 이미 서버에 보낸 요청은 결과를 확인하고 기록한다. 설정은 다음 실행에도 유지된다. 0.4.32부터 수집·교배·합성·거래 메뉴와 물고기 목록은 관찰용으로 취급하며, 열어둔 상태에서도 자동 실행을 계속한다. 실제 통신 처리·확인 대화상자·미확정 요청은 계속 대기하며, 레벨업 보상 팝업은 기존 전용 경로에서 처리한다. 자동 교배는 게임의 교배 화면에 자동으로 고른 부모를 설정하므로 화면의 선택 내용이 바뀔 수 있다. BepInEx 콘솔은 이 PC에서 숨김으로 설정했다.

0.2.1에서는 메뉴를 닫은 뒤 남아 있는 `currentMenuType`을 사용 중 상태로 오판하던 문제를 수정했다. 기존 판정은 탭 값이 Home이 아니면 대기했지만, 이제 창·보조 화면의 실제 `activeInHierarchy`와 네트워크·확인창 상태를 판정한다. 같은 수정이 자동 레벨업의 홈 상태 판단에도 적용된다. `snapshot.json`의 `window_open`, `overlay_open`, `menu_name`, `ui_block_reason`으로 어떤 실제 화면이 대기를 유발했는지 확인할 수 있다. 상태 메시지에 이전의 `Observation mode`가 남지 않도록 대기 이유도 매번 갱신한다.

설정 파일: `C:\Program Files (x86)\Steam\steamapps\common\PC FISH\BepInEx\config\pcfish-automation.json`.

## 두 실행 모드

### Protected: 보호된 물고기를 제외하는 진행 모드

- 잠금, 시즌 어종, 수동 예약한 ID/어종은 교배와 일반 합성에서 모두 제외한다. 시즌 레시피 자동 예약은 일반 합성만 막고, 일반 재료의 교배는 허용한다. 시즌 제작의 이전 등급 재료 예외는 위 정책을 따른다. `protection_mode=market`이면 위 시세 보호 상태를 사용하고, `grade`이면 기존처럼 **Grade 3 이상**을 추가로 제외한다.
- 보호 대상과 시즌 필요 수량을 제외한 일반 물고기 10마리를 모아 합성한다. 남은 교배 횟수가 있거나 교배 쿨타임 중이어도 합성할 수 있다. 기본종은 제외한다.
- 같은 Level·Grade 열 마리 묶음을 우선한다. 없으면 같은 Grade에서 Level 차이가 최대 1인 열 마리 묶음을 찾는다. 각 묶음에서는 남은 교배 횟수가 적은 개체부터 고르고, 후보 중 평균 Level이 높은 묶음을 우선한다. 실행 직전에도 별 등급 동일·희귀도 차이 최대 1·최저 예측 결과가 가장 높은 재료 이상인지 확인한다. 허용되는 묶음이 없으면 교배 계획을 판단한다.
- 합성 결과를 받은 뒤 다시 교배를 계획한다.
- 교배는 현재 부모와 곧 쿨타임이 끝나는 부모, 하트 회복 시각을 함께 비교한다. 현재 알고 있는 부모만 대상으로 15분·최대 3회 행동을 탐색한다. 부모 후보 최대 24마리, 각 상태의 즉시 조합 최대 16개, 노드 4,000개로 제한한다.
- 목적 점수는 확인한 클라이언트 Level 예측표와 정책 가중치 `Level 1..5 → 1,2,4,10,25`를 쓴다. 빠른 결과에 `exp(-대기초/900)` 시간 가중치를 적용한다. 이 값은 **원화 가격, 별 등급 확률, 판매 수익 예측이 아니다**.
- 아직 태어나지 않은 자식의 어종·Grade와 기본종의 성장 회복 시간은 만들지 않는다. 실제 결과와 성장을 다시 읽어 판단한다. 새 물고기는 게임의 기본 보관 상태를 유지한다.

이 모드의 행동 점수는 Level 진행을 위한 정책이다. 판매 수익을 최적화했다는 의미는 아니다. 시세 보호 상태는 후보의 보존 여부에만 사용한다. 비싼 특정 개체를 알고 있다면 `reserved_ids` 또는 `reserved_species`에 추가하거나 게임에서 잠근다. `grade` 정책에서는 `protect_grade_at_least`를 2로 낮추면 2성부터 보존한다. 지원 범위는 2~5이고 이 정책에서는 5성이 항상 보호된다.

### Economic: 기존 수익 기대값 계획기


`economic_model_file`에 기존 계획기 계약에 맞는 JSON 파일을 지정해야 한다. 해당 파일의 시세·공동 결과 규칙을 사용하고 보유 목록과 하트는 실제 게임 상태로 덮어쓴다. 이 경로는 `src/pcfish_planner/engine.py`의 기대값 탐색을 그대로 사용한다.

## 실행 보호와 결과 기록

게임 메인 스레드에서 상태를 1초마다 읽는다. 별도 Python 프로세스는 2초마다 추천을 갱신한다. 두 프로세스는 로컬 JSON 파일로만 통신한다. Python은 직접 게임 서버에 요청하지 않는다.

추천에는 실행 세션 ID, 보유 상태 해시, 설정 해시와 짧은 유효기간을 넣는다. 실행 직전에 게임 쪽에서 물고기 존재·중복·교배 잔여 횟수·성장·하트·보유 상한·잠금·시즌·별 등급·예약·게임 조작 중 여부를 다시 확인한다. 한 요청의 결과를 확인하기 전에는 다음 요청을 보내지 않는다. 성공 처리에서 기존 UI와 같은 경험치·하트 소비·저장 동작을 수행한다. 하트가 가득 찼으면 기존 UI처럼 소비 직전에 회복 기준 시각을 초기화한다.

요청 전 `pending.json`과 복구 단계를 디스크에 쓴다. 0.4.12는 통신 지연·60초 초과·미완료 요청이 남은 재시작에서 `waiting_network`로 낮은 빈도의 결과 확인을 계속한다. 소비 요청은 재시도하지 않는다. 확인 완료 후 원본 미완료 기록을 보관 이동하고 자동 재개한다. 실제 자원 손실·서로 다른 성공 UID·계정 불일치·비용 저장 도중의 중단 등 결과를 안전하게 확정할 수 없는 경우에는 `uncertain`과 원본 기록을 유지한다. Pause/Protected 전환으로 미확정 기록을 삭제하거나 무시하지 않는다.

위 전체 중단은 이미 발송한 교배·합성·제작 요청을 중복 실행할 위험이 있는 경우에 적용한다. 레벨업의 일반적인 관찰 차이나 표시 기능 문제에는 적용하지 않는다. 실제 손실을 확인한 레벨업은 `consumption-alert.json`에 근거를 남겨 재시작으로 중단이 풀리지 않게 한다. `status.json`의 `level_up_paused`·`level_up_note`와 `display_note`·`market_lock_note`는 부가 기능 상태를 따로 표시한다.

## 빌드·설치·제거

공개 저장소에는 로더, .NET SDK와 게임에서 생성한 interop DLL이 포함되지 않는다. 처음 설치하는 환경에서는 다음 준비가 필요하다.

1. Python 3.12 이상으로 저장소의 `.venv`를 만든다. 시세 보호를 사용하려면 Google Chrome을 설치하고 `.venv\Scripts\python.exe -m pip install -e '.[automation]'`으로 Selenium 의존성도 준비한다. Selenium Manager는 첫 조회에서 해당 크롬에 맞는 ChromeDriver를 내려받아 캐시한다. 게임 설정의 `python_path`는 이 `.venv`의 실제 실행 파일을 가리켜야 한다. 독립 계획기나 기존 Grade 보호만 사용한다면 기본 Python 설치로도 실행할 수 있다.
2. 공식 BepInEx `6.0.0-be.793+dbc82f0` Windows x64 IL2CPP 패키지를 별도로 받아 `tools/BepInEx-IL2CPP-be793`에 푼다. 이 폴더 바로 아래에 패키지의 `BepInEx` 폴더와 로더 파일이 있어야 한다.
3. 게임을 종료하고 `scripts/Install-Mod.ps1 -LoaderOnly`를 실행한다. 게임을 한 번 실행해 `BepInEx/interop` 참조 파일을 생성한 뒤 다시 종료한다.
4. .NET 8 SDK를 `tools/dotnet`에 준비한 뒤 아래 `Build-Mod.ps1`로 빌드한다. 시스템 SDK를 사용한다면 저장소 루트에서 `dotnet build mod/PCFish.Automation/PCFish.Automation.csproj -c Release`로 직접 빌드할 수도 있다. 게임 경로가 기본값과 다르면 `-p:GameRoot="실제 게임 경로"`를 지정한다.
5. `mod/pcfish-automation.json`의 `python_path`와 `project_root`를 실제 절대 경로로 바꾼 뒤 플러그인을 설치한다. 기존 게임 폴더의 설정이 이미 있으면 설치 스크립트가 덮어쓰지 않으므로 그 파일도 직접 확인한다.

아래 명령의 `C:\Project\PC-fish`는 예시 저장소 경로다. 설치·빌드 스크립트에는 필요에 따라 `-GameRoot`를 지정한다.

```powershell
& 'C:\Project\PC-fish\scripts\Build-Mod.ps1'
# 게임을 정상 종료한 다음:
& 'C:\Project\PC-fish\scripts\Install-Mod.ps1'
# 제거도 게임을 정상 종료한 다음:
& 'C:\Project\PC-fish\scripts\Remove-Mod.ps1'
```

로더는 공식 BepInEx `6.0.0-be.793+dbc82f0` IL2CPP x64 빌드이고 플러그인은 net6.0이다. 로컬 SDK는 `tools/dotnet`에 설치했다. 설치 기록 `var/mod-installation.json`은 설치한 파일과 기존 파일 백업을 추적한다. 제거는 기록에 있는 파일만 삭제/복원하고 세이브 진행 상황은 되돌리지 않는다. 처음 설치할 때와 자동 실행을 켜기 전에 ES3 세이브를 별도 백업했다. 자동 실행 직전 백업은 `work/mod-20261106/pre-activation`에 있다.

검증한 GameAssembly SHA-256은 `F5F98F82FE2FED5F177B440DF07C9084C814EB8C5C9A141661A67FF184149F93`이다. 설치 시와 플러그인 로드 시 모두 확인한다. Steam 업데이트로 바뀌면 재분석 전 실행하지 않는다.

공식 로더 자료: [IL2CPP 설치 안내](https://docs.bepinex.dev/master/articles/user_guide/installation/unity_il2cpp.html), [BepInEx 빌드](https://builds.bepinex.dev/projects/bepinex_be).
